# คู่มือสำรองและกู้คืนข้อมูล — Krirk Verify (F-OPS-04)

> ใช้กับการติดตั้งตาม [`deployment.md`](deployment.md) (Docker Compose production) · คำสั่งทั้งหมดรันจาก `/opt/krirk-verify` ด้วยผู้ใช้ที่อยู่ในกลุ่ม `docker`

## 1. สิ่งที่ต้องสำรอง

| รายการ | อยู่ที่ | สำรองด้วย | ความถี่ |
|--------|--------|-----------|---------|
| ฐานข้อมูล PostgreSQL | volume `krirk-verify_postgres_data` | `scripts/backup-db.sh` | ทุกวัน (cron 01:30) + ก่อนอัปเดตทุกครั้ง |
| **`ENCRYPTION_KEY`, `IDENTIFIER_PEPPER`** | `.env.prod` | จดเก็บใน password manager / ตู้เซฟของหน่วยงาน **แยกจากไฟล์สำรองฐานข้อมูล** | ครั้งเดียวตอนติดตั้ง |
| `.env.prod` ทั้งไฟล์ | รากโปรเจกต์ | สำเนาเข้ารหัส เก็บแยกจากเซิร์ฟเวอร์ | เมื่อแก้ไข |
| ใบรับรอง TLS | `docker/nginx/certs/` | ตามกระบวนการต่ออายุใบรับรองของมหาวิทยาลัย | เมื่อต่ออายุ |

> ⚠ **ไฟล์สำรองฐานข้อมูลโดยไม่มี `ENCRYPTION_KEY` + `IDENTIFIER_PEPPER` ชุดเดิม กู้คืนได้แต่ใช้งานไม่ได้** — เลขบัตรที่เข้ารหัสจะถอดไม่ได้ และค้นหาด้วยเลขบัตร/พาสปอร์ตจะไม่พบข้อมูลเดิม
>
> ⚠ **อย่าเก็บคีย์ไว้คู่กับไฟล์สำรอง** — ถ้าไฟล์สำรองรั่วพร้อมคีย์ ข้อมูลส่วนบุคคลจะถูกถอดรหัสได้ทั้งหมด

ไม่ต้องสำรอง: image ของแอป (build ใหม่จาก git tag ได้) และ container อื่น ๆ (ไม่มีสถานะ)

## 2. สำรองข้อมูล

```bash
scripts/backup-db.sh
```

สคริปต์ทำตามลำดับ:

1. รัน `pg_dump --format=custom` ภายใน container `postgres` (บีบอัดในตัว ไม่ต้องหยุดระบบ ได้ snapshot ที่สอดคล้องกัน ณ เวลาเริ่ม)
2. เขียนไฟล์เป็น `.partial` แล้วตรวจว่าอ่านกลับได้ด้วย `pg_restore --list` — ถ้าไม่ผ่านจะลบทิ้งและจบด้วย exit 1
3. เปลี่ยนชื่อเป็น `backups/krirk_verify-YYYYmmdd-HHMMSS.dump` และสร้างไฟล์ `.sha256` คู่กัน (สิทธิ์ไฟล์ 600)
4. ลบไฟล์สำรองที่เก่ากว่า `BACKUP_KEEP_DAYS` วัน (ค่าเริ่มต้น 30)

ตัวอย่างผลลัพธ์:

```
[2026-09-16 21:47:21] เริ่มสำรองข้อมูล → /opt/krirk-verify/backups/krirk_verify-20260916-214721.dump
[2026-09-16 21:47:23] ✔ สำเร็จ ขนาด 92K
[2026-09-16 21:47:23] ลบไฟล์สำรองที่เก่ากว่า 30 วัน: 0 ไฟล์
```

### ตั้งค่า

| ตัวแปรใน `.env.prod` | ค่าเริ่มต้น | ความหมาย |
|----------------------|-------------|----------|
| `BACKUP_DIR` | `./backups` | โฟลเดอร์ปลายทาง (path สัมพัทธ์นับจากรากโปรเจกต์) — ควรเป็นดิสก์คนละลูกกับ volume ของ Docker |
| `BACKUP_KEEP_DAYS` | `30` | จำนวนวันที่เก็บไฟล์ไว้บนเครื่อง · `0` = ไม่ลบ |

### สำเนานอกเครื่อง (off-site)

ไฟล์ใน `backups/` อยู่บนเครื่องเดียวกับฐานข้อมูล ถ้าเครื่องเสียหายจะหายไปพร้อมกัน ให้คัดลอกออกนอกเครื่องทุกวันตามนโยบายของมหาวิทยาลัย เช่น เพิ่มใน cron หลังงานสำรอง:

```
15 2 * * *  krirk  rsync -a /opt/krirk-verify/backups/ backup-host:/srv/backup/krirk-verify/ >> /var/log/krirk-verify/cron.log 2>&1
```

ปลายทางต้องจำกัดสิทธิ์การเข้าถึง เพราะไฟล์สำรองมีข้อมูลส่วนบุคคล (ชื่อ วุฒิ อีเมลผู้ใช้ Audit Log)

## 3. กู้คืนข้อมูล

```bash
scripts/restore-db.sh backups/krirk_verify-20260916-013000.dump
```

สคริปต์ทำตามลำดับ:

1. ตรวจ checksum กับไฟล์ `.sha256` (ถ้ามี) และตรวจว่าเป็นไฟล์ pg_dump ที่อ่านได้
2. ให้พิมพ์ชื่อฐานข้อมูลเพื่อยืนยัน (ข้ามด้วย `--yes` สำหรับสคริปต์อัตโนมัติ)
3. หยุด `nginx` และ `app` — ผู้ใช้จะเข้าระบบไม่ได้ระหว่างกู้คืน
4. **สำรองสถานะปัจจุบันก่อน** ด้วย `backup-db.sh` (เผื่อกู้คืนผิดไฟล์และต้องย้อนกลับ)
5. `pg_restore --clean --if-exists --single-transaction` — ถ้าผิดพลาดกลางทาง ฐานข้อมูลคงสถานะเดิมทั้งหมด
6. รัน `migrate` เพื่อใช้ migration ที่ใหม่กว่าไฟล์สำรอง (ถ้ามี)
7. เปิด `app` และ `nginx` แล้วรอ health check ผ่าน (สูงสุด 150 วินาที)

ตัวอย่างผลลัพธ์:

```
[2026-09-16 21:51:20] ✔ checksum ถูกต้อง
[2026-09-16 21:51:21] หยุดแอปและ nginx ระหว่างกู้คืน
[2026-09-16 21:51:23] สำรองสถานะปัจจุบันก่อนกู้คืน (เผื่อต้องย้อนกลับ)
[2026-09-16 21:51:26] กู้คืนจาก backups/krirk_verify-20260916-214741.dump
[2026-09-16 21:51:27] ใช้ migration ที่ใหม่กว่าไฟล์สำรอง (ถ้ามี)
[2026-09-16 21:51:36] เปิดแอป
[2026-09-16 21:51:51] ✔ กู้คืนเสร็จ และ health check ผ่าน
```

### หลังกู้คืน

- [ ] ล็อกอินผู้ดูแล → เปิดคำขอที่อนุมัติแล้ว 1 รายการ → ข้อมูลผลตรวจสอบแสดงครบ (ยืนยันว่า `ENCRYPTION_KEY` ถูกชุด)
- [ ] หน้า **ข้อมูลผู้สำเร็จการศึกษา** ค้นหาด้วยเลขบัตรที่ทราบว่ามีอยู่ → พบ (ยืนยันว่า `IDENTIFIER_PEPPER` ถูกชุด)
- [ ] กด **ซิงก์ทั้งหมดตอนนี้** ที่หน้าซิงก์ข้อมูล เพื่อดึงข้อมูลทะเบียนที่เปลี่ยนหลังเวลาสำรอง
- [ ] แจ้งผู้เกี่ยวข้องว่าคำขอ/การเปลี่ยนแปลงที่เกิดหลังเวลาของไฟล์สำรองหายไป และต้องยื่นหรือทำซ้ำ
- [ ] บันทึกเหตุการณ์ (เวลา ไฟล์ที่ใช้ เหตุผล ผู้ดำเนินการ) ตามกระบวนการรับมือเหตุการณ์ด้าน PDPA ของมหาวิทยาลัย

## 4. สถานการณ์ที่พบบ่อย

### 4.1 อัปเดตเวอร์ชันแล้วมีปัญหา ต้องย้อนกลับ

```bash
git checkout <tag เดิม>
kv build
scripts/restore-db.sh backups/<ไฟล์ที่สำรองก่อนอัปเดต>.dump
```

migration ของ Prisma ย้อนกลับไม่ได้ จึงต้องกู้ฐานข้อมูลจากไฟล์ก่อนอัปเดตคู่กับโค้ดเวอร์ชันเดิมเสมอ

### 4.2 ย้ายไปเครื่องใหม่

1. เครื่องใหม่: ติดตั้งตาม `deployment.md` ข้อ 3.1–3.4 โดยใช้ `.env.prod` **ชุดเดิม** (คีย์ต้องตรงกัน)
2. เครื่องเก่า: `scripts/backup-db.sh` แล้วคัดลอกไฟล์ `.dump` + `.sha256` ไปเครื่องใหม่
3. เครื่องใหม่: `scripts/restore-db.sh backups/<ไฟล์>.dump`
4. เปลี่ยน DNS → ปิดเครื่องเก่า (หยุด cron ของเครื่องเก่าก่อน เพื่อไม่ให้ sync/ส่งอีเมลซ้ำ)

### 4.3 ต้องการตรวจไฟล์สำรองโดยไม่กระทบระบบจริง

กู้คืนเข้าฐานข้อมูลชั่วคราวใน container แยก:

```bash
docker run -d --name kv-restore-test -e POSTGRES_PASSWORD=test postgres:16-alpine
sleep 5
docker exec -i kv-restore-test pg_restore -U postgres -d postgres --no-owner < backups/<ไฟล์>.dump
docker exec kv-restore-test psql -U postgres -c "select count(*) from verification_requests"
docker rm -f kv-restore-test
```

แนะนำให้ทดสอบกู้คืนแบบนี้อย่างน้อยเดือนละครั้ง — ไฟล์สำรองที่ไม่เคยทดสอบกู้คืนถือว่ายังไม่มีการสำรอง

## 5. ข้อจำกัด

- สำรองแบบ logical dump รายวัน → กู้คืนได้ถึงเวลาของไฟล์ล่าสุดเท่านั้น (RPO สูงสุด ~24 ชั่วโมง) · ถ้ามหาวิทยาลัยต้องการ RPO ต่ำกว่านี้ ให้เพิ่มรอบใน cron หรือใช้ WAL archiving / point-in-time recovery ของ PostgreSQL
- ไฟล์สำรองไม่ได้เข้ารหัสทั้งไฟล์ (เลขบัตรในฐานข้อมูลเข้ารหัสอยู่แล้ว แต่ชื่อ วุฒิ และ Audit Log ไม่ได้เข้ารหัส) · ถ้าส่งออกนอกเครื่องผ่านสื่อที่ไม่ปลอดภัย ให้เข้ารหัสเพิ่ม เช่น `gpg --symmetric`
