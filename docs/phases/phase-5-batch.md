## สรุปสั้น

หน่วยงานภายนอกดาวน์โหลดเทมเพลต (CSV หรือ Excel) กรอกคอลัมน์ `search_type` และ `search_value` แล้วอัปโหลด · ระบบตรวจทีละแถวและเก็บเป็นงานสถานะ **รอยืนยัน** ให้ดูตัวอย่างก่อน · เมื่อกดยืนยันจะยื่นคำขอจริงทีละแถวเบื้องหลังด้วยกฎ auto-approve ชุดเดียวกับคำขอเดี่ยว พร้อมแถบความคืบหน้า · จบแล้วดูผลรายแถว สรุป 4 ตัวเลข และ export เป็น Excel ได้ · โควตาแบบชุดนับเป็น "แถวต่อวัน" แยกจากคำขอเดี่ยวโดยสิ้นเชิง

## การตัดสินใจเชิงออกแบบ

- **ไม่เก็บคีย์ค้นหาเป็น plaintext** — `BatchItem` เก็บ ciphertext (AES-256-GCM) ไว้ประมวลผล และค่าที่ mask แล้วไว้แสดงผล ใช้ตัวช่วยชุดเดียวกับคำขอเดี่ยว (PDPA ข้อ 4.5)
- **ตัวอย่างก่อนยืนยันถูกเก็บในฐานข้อมูล** (สถานะ DRAFT) ไม่ใช่ในหน่วยความจำ — ปิดแท็บแล้วกลับมายืนยันต่อได้ และผลการตรวจแถวไม่ถูกคำนวณซ้ำ
- **ตัวตรวจแถวเป็นฟังก์ชันล้วนแยกจากการอ่านไฟล์** (`rows.ts` ไม่แตะ I/O) จึงเขียน unit test ครอบคลุมทุกสาขาได้โดยไม่ต้องใช้ฐานข้อมูลหรือไฟล์จริง
- **ยื่นคำขอผ่าน `verification.service` เดิมทุกแถว** — กฎ auto-approve, snapshot, audit และการกันเดาเลขบัตรจึงเป็นชุดเดียวกับคำขอเดี่ยว ไม่มีตรรกะซ้ำสองที่
- **สถานะรายแถวที่แสดงผลอ่านจากสถานะล่าสุดของคำขอ** ไม่ใช่สถานะตอนสร้าง — เจ้าหน้าที่อนุมัติ/ปฏิเสธภายหลังแล้วหน้าผลลัพธ์ของชุดอัปเดตตาม
- **ระวังหลุมของ bundler:** `rows.ts` เรียก `@/lib/crypto` ซึ่งใช้ `node:crypto` คอมโพเนนต์ฝั่ง client จึงรับค่าคงที่ (จำนวนแถวสูงสุด, รายการวัตถุประสงค์) เป็น props แทนการ import

## วิธีทดสอบด้วยตนเอง

1. ล็อกอิน `hr@thaihr.co.th` → เมนู **ตรวจสอบแบบชุด** → กด **เทมเพลต CSV**
2. กรอกไฟล์ให้มีทั้งแถวที่ถูกต้องและผิด เช่น `CITIZEN_ID,1101700230708` และ `CITIZEN_ID,1234567890123`
3. ลากไฟล์มาวาง → เลือกวัตถุประสงค์ → ติ๊ก PDPA → **อัปโหลดและตรวจไฟล์** → ดูเหตุผลรายแถวก่อนยืนยัน
4. **ยืนยันและเริ่มตรวจสอบ** → ดูแถบความคืบหน้าเดินจนครบ → กดเลขอ้างอิงเพื่อเปิดคำขอรายตัว
5. **Export Excel** → เปิดไฟล์ตรวจว่าไม่มีเลขบัตรเต็ม
6. อัปโหลดไฟล์ใหญ่ซ้ำ ๆ จนเกิน 500 แถว/วัน → ระบบปฏิเสธพร้อมข้อความโควตา (ดูบันทึกใน `/staff/audit-logs` action `batch.rate_limited`)

## ข้อจำกัดที่ทราบ / ส่งต่อ Phase ถัดไป

- **ทางลัด "ตรวจสอบแบบชุด" และ "ดาวน์โหลดเทมเพลต CSV" บนแดชบอร์ดผู้ขอยังซ่อนอยู่** ตามที่อนุมัติไว้ใน Phase 6 (ข้อ 6) — ตอนนี้หน้าพร้อมแล้ว ควรเปิดคืนในรอบถัดไป (เมนูด้านข้างและ bottom nav เปิดใช้งานแล้ว)
- **งานที่ค้างสถานะ PROCESSING** เกิดได้ถ้า process ถูกรีสตาร์ตระหว่าง `after()` ทำงาน — ยังไม่มีตัวกู้คืน ควรเพิ่มการกวาดใน Phase 10
- **ประมวลผลทีละแถวตามลำดับ** (ไม่ขนาน) เพื่อไม่ให้กระแทกฐานข้อมูล — 500 แถวใช้เวลาพอสมควร ถ้าโหลดสูงขึ้นค่อยพิจารณาเพิ่ม worker
- **ไฟล์ .xlsx ถูกอ่านทั้งไฟล์เข้าหน่วยความจำ** — จำกัดด้วยขนาด 2 MB และ 500 แถว
- **`batch_jobs` / `batch_items` ยังไม่อยู่ในนโยบาย retention** (เช่นเดียวกับ `email_logs` ของ Phase 9) — ควรรวมเข้ากับงาน retention ใน Phase 10
