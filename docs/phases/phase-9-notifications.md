## สรุปสั้น

อีเมลทุกฉบับผ่านทางเข้าเดียวที่บันทึก `EmailLog` ก่อนส่ง · ฉบับที่ล้มเหลวถูกส่งซ้ำอัตโนมัติตามรอบ และผู้ดูแลกดส่งซ้ำเองได้จากหน้า `/staff/email-logs` · เจ้าหน้าที่ได้สรุปคิวคำขอทางอีเมลวันละครั้งแทนการแจ้งรายคำขอ · กระดิ่งบน header แสดงการแจ้งเตือนในระบบจากเหตุการณ์จริง 6 ชนิด พร้อมหน้ารายการทั้งหมดที่ `/notifications`

## การตัดสินใจเชิงออกแบบ

- **`EmailLog` เก็บ payload ไม่ใช่ HTML** — retry จะ render ใหม่ด้วยโค้ดและไฟล์แปลล่าสุด ไม่เก็บเนื้อหาอีเมลซ้ำในฐานข้อมูล และแก้เทมเพลตแล้วอีเมลที่ยังไม่ได้ส่งได้ผลลัพธ์ใหม่ทันที
- **การแจ้งเตือนเก็บเป็น `type` + `params`** แล้วแปลตอนแสดงผล — ผู้ใช้ที่สลับภาษาเห็นข้อความตามภาษาที่เลือกอยู่เสมอ (ถ้าเก็บข้อความสำเร็จรูปจะค้างภาษาเดิม)
- **แจ้งเจ้าหน้าที่สองชั้นตามเจตนาของ spec** — ในระบบแจ้งทันทีรายคำขอ (กระดิ่ง) ส่วนอีเมลเป็นสรุปรายวันเพื่อไม่ให้อีเมลท่วมตามข้อกำหนด F-NOT-03
- **`dedupeKey` + unique `(userId, dedupeKey)`** กันการแจ้งซ้ำเมื่อ cron ถูกเรียกหลายครั้ง (เช่น สรุป SLA ของวันเดียวกัน) โดยไม่ต้องตรวจก่อนเขียน
- **ส่งซ้ำได้เฉพาะฉบับที่สถานะ `FAILED`** — ฉบับที่ส่งสำเร็จแล้วต้องไม่ถูกส่งซ้ำโดยไม่ตั้งใจ
- **บั๊กที่เทสต์จับได้:** ตัวตรวจชื่อเทมเพลตเดิมใช้ `value in EMAIL_TEMPLATES` ซึ่งเป็นจริงกับ `constructor`/`toString` ที่สืบทอดจาก `Object.prototype` ทำให้ retry หยิบค่าที่ไม่ใช่เทมเพลตไปใช้แล้วพัง — เปลี่ยนเป็น `Object.hasOwn()`

## วิธีทดสอบด้วยตนเอง

1. ล็อกอิน `registrar@krirk.ac.th` → ยื่นคำขอที่เข้าคิวจากบัญชี `hr@thaihr.co.th` → รีเฟรชหน้าเจ้าหน้าที่ → **กระดิ่งมีจุดแดง** → เปิดแล้วกดรายการเพื่อไปหน้าพิจารณา
2. ผู้ดูแล → ตั้งค่าระบบ → กลุ่ม **การแจ้งเตือน** → เปิด/ปิด "ส่งสรุปคิวคำขอรายวันทางอีเมล"
3. `curl -X POST -H "x-cron-secret: $CRON_SECRET" http://localhost:3000/api/cron/queue-digest` → ดูอีเมลสรุปที่ Mailpit http://localhost:8025 → เรียกซ้ำได้ `alreadySent`
4. ปิด Mailpit (`docker stop krirk-verify-mailpit`) แล้วกด "ส่งลิงก์ตั้งรหัสผ่านใหม่" → เปิด `/staff/email-logs` เห็นแถวสถานะ **ส่งไม่สำเร็จ** → เปิด Mailpit แล้วกด **ส่งซ้ำ** → สถานะเปลี่ยนเป็นส่งแล้ว
5. `curl -X POST -H "x-cron-secret: $CRON_SECRET" http://localhost:3000/api/cron/email-retry` → ส่งซ้ำอัตโนมัติทุกฉบับที่ถึงกำหนด

## ข้อจำกัดที่ทราบ / ส่งต่อ Phase ถัดไป

- **แถวสถานะ `PENDING` ที่ค้าง** เกิดได้เฉพาะกรณี process ดับระหว่างสร้าง log กับอัปเดตผลการส่ง · งาน retry หยิบเฉพาะ `FAILED` จึงไม่เก็บกวาดให้ — ควรเพิ่มการกวาด `PENDING` ที่เก่ากว่า N นาทีใน Phase 10
- **กระดิ่งอัปเดตเมื่อโหลดหน้าใหม่** (ไม่มี WebSocket/polling) — เพียงพอสำหรับงานสำนักงาน และไม่เพิ่ม service ตามหมายเหตุสถาปนิก
- **ยังไม่ได้ทดสอบกับ SMTP จริงของมหาวิทยาลัย** (ข้อ 10 รายการที่ 3) — dev ใช้ Mailpit · ค่า `SMTP_SECURE`/`SMTP_USER` เตรียมไว้ใน `.env.example` แล้ว
- **e2e ของสรุปรายวันยอมรับผลได้หลายแบบ** (`sent` / `empty` / `alreadySent`) เพราะขึ้นกับจำนวนคำขอในคิวและรอบที่เคยส่งของวันนั้น
- **`EmailLog` ยังไม่มีนโยบายเก็บรักษา** — ควรรวมเข้ากับงาน retention ใน Phase 10 (ปัจจุบัน retention ครอบคลุมคำขอและ audit log)
