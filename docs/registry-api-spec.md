# ข้อกำหนด API ที่ขอจากระบบทะเบียน — Krirk Verify (F-OPS-08)

| รายการ | รายละเอียด |
|--------|------------|
| ส่งถึง | ฝ่ายทะเบียนและประมวลผล / สำนักคอมพิวเตอร์ มหาวิทยาลัยเกริก |
| จาก | ทีมพัฒนาระบบตรวจสอบวุฒิการศึกษาออนไลน์ (Krirk Verify) |
| เวอร์ชันเอกสาร | ร่าง 1.0 — 16 กันยายน 2569 |
| สถานะ | รอฝ่ายทะเบียนยืนยันหรือเสนอรูปแบบที่มีอยู่แล้ว (spec ข้อ 10 รายการที่ 1–2) |

## 1. วัตถุประสงค์

Krirk Verify ต้องดึงข้อมูล **ผู้สำเร็จการศึกษาและนักศึกษา** จากระบบทะเบียนมาเก็บสำเนาไว้ (sync) เพื่อให้ตรวจสอบวุฒิได้ตลอดเวลา แม้ระบบทะเบียนปิดปรับปรุง

- **ใช้อ่านอย่างเดียว** — Krirk Verify ไม่เขียนข้อมูลกลับไปที่ระบบทะเบียน
- **รูปแบบในเอกสารนี้เป็นข้อเสนอ** — ระบบทำงานกับ Mock API รูปแบบนี้ได้ครบแล้ว ถ้า API จริงต่างออกไป เราจะแก้เฉพาะตัวแปลงข้อมูล (adapter) ไม่กระทบส่วนอื่น จึงขอให้ส่ง spec ที่มีอยู่จริงมาได้เลย ไม่จำเป็นต้องทำตามเอกสารนี้ทุกข้อ
- **ข้อมูลที่ขอเป็นชุดขั้นต่ำ** ที่ต้องใช้แสดงผลตรวจสอบวุฒิ (spec R-07) และจับคู่ด้วยเลขบัตร/พาสปอร์ต — ไม่ขอที่อยู่ เบอร์โทร ผลการเรียนรายวิชา หรือข้อมูลอื่นที่ไม่จำเป็นตาม PDPA

## 3. การเชื่อมต่อและความปลอดภัย

| หัวข้อ | ข้อเสนอ |
|--------|---------|
| Protocol | HTTPS (TLS 1.2 ขึ้นไป) เท่านั้น |
| Base URL | เช่น `https://registry.krirk.ac.th/api/v1` — ตั้งผ่าน `REGISTRY_API_URL` |
| ยืนยันตัวตน | `Authorization: Bearer <API key>` — ตั้งผ่าน `REGISTRY_API_KEY` · ถ้าระบบทะเบียนใช้วิธีอื่น (mTLS, OAuth2 client credentials, IP allowlist) แจ้งได้ |
| สิทธิ์ของ key | อ่านอย่างเดียว เฉพาะ endpoint ในเอกสารนี้ |
| รูปแบบข้อมูล | `application/json; charset=utf-8` |
| วันที่ | `YYYY-MM-DD` (ค.ศ.) |
| เวลา | ISO 8601 พร้อม timezone เช่น `2026-09-15T14:30:00+07:00` |
| Timeout ฝั่งเรา | 10 วินาทีต่อคำขอ · retry สูงสุด 3 ครั้งแบบ exponential backoff (0.5 / 1 / 2 วินาที) เฉพาะ timeout, network error, HTTP 429 และ 5xx |
| ปริมาณการเรียก | sync เต็มชุด **วันละ 1 ครั้ง** (ค่าเริ่มต้น 02:00 น.) ครั้งละ 500 ระเบียนต่อหน้าตามลำดับ (ไม่ยิงขนาน) · sync เฉพาะที่เปลี่ยนรายชั่วโมง (ถ้าอนุญาต) · ดึงรายคนเมื่อเจ้าหน้าที่กดปุ่ม (ไม่กี่ครั้งต่อวัน) · ตรวจสถานะเมื่อเปิดหน้าซิงก์ข้อมูล |

## 4. Endpoints

### 4.1 `GET /health` — ตรวจสถานะ

ใช้แสดงสถานะการเชื่อมต่อบนหน้าเจ้าหน้าที่และ `/api/health` ของระบบ (timeout 3 วินาที ไม่ retry) — ฝั่งเราดูเพียงว่าตอบ HTTP 2xx

```http
GET /api/v1/health
Authorization: Bearer <API key>
```

```json
{ "status": "ok" }
```

### 4.2 `GET /students` — รายการนักศึกษาแบบแบ่งหน้า

| Query | ชนิด | จำเป็น | คำอธิบาย |
|-------|------|:------:|----------|
| `page` | integer ≥ 1 | ✔ | หน้าที่ต้องการ |
| `pageSize` | integer 1–1000 | ✔ | จำนวนระเบียนต่อหน้า (เราใช้ 500) |
| `updatedSince` | ISO 8601 datetime | | คืนเฉพาะระเบียนที่ `updatedAt` **มากกว่า** ค่านี้ — ใช้กับ sync เฉพาะที่เปลี่ยน · ไม่ส่ง = ทุกระเบียน |

```http
GET /api/v1/students?page=1&pageSize=500&updatedSince=2026-09-14T02:00:00%2B07:00
Authorization: Bearer <API key>
```

```json
{
  "items": [ { "...": "Student object ตามข้อ 5" } ],
  "page": 1,
  "pageSize": 500,
  "total": 12840,
  "hasMore": true
}
```

ข้อกำหนด:

- **ลำดับต้องคงที่ระหว่างหน้า** (เช่น เรียงตาม `studentCode`) เพื่อไม่ให้ระเบียนหายหรือซ้ำระหว่างดึงหลายหน้า
- `hasMore = false` ที่หน้าสุดท้าย · ฝั่งเราหยุดเมื่อ `hasMore` เป็น false หรือได้ `items` ว่าง
- ระเบียนที่รูปแบบไม่ถูกต้องจะถูกข้ามทีละรายการ (นับเป็น "ไม่ถูกต้อง" ในประวัติ sync) — ไม่ทำให้ทั้งหน้าล้ม
- ถ้า `updatedSince` ทำไม่ได้ ระบบยังทำงานได้ด้วย sync เต็มชุดรายวันอย่างเดียว

### 4.3 `GET /students/{studentCode}` — ข้อมูลรายคน

ใช้เมื่อเจ้าหน้าที่กด **ดึงข้อมูลใหม่** ในหน้าพิจารณาคำขอ เพื่อได้สถานภาพล่าสุดก่อนตัดสิน

```http
GET /api/v1/students/6112345679
Authorization: Bearer <API key>
```

- `200` → Student object ตามข้อ 5 (ไม่ห่อด้วย envelope)
- `404` → ไม่พบรหัสนักศึกษานี้

### 4.4 HTTP status ที่ฝั่งเราจัดการ

| Status | ความหมายฝั่งเรา | retry |
|--------|-----------------|:-----:|
| 2xx | สำเร็จ | — |
| 401 / 403 | API key ผิดหรือหมดสิทธิ์ (`UNAUTHORIZED`) | ✘ |
| 404 | ไม่พบ (เฉพาะข้อ 4.3) | ✘ |
| 429 | เกิน rate limit (`RATE_LIMITED`) — ถ้าส่ง `Retry-After` มาด้วยจะช่วยให้ปรับรอบได้ในอนาคต | ✔ |
| 5xx | ระบบทะเบียนขัดข้อง (`SERVER_ERROR`) | ✔ |
| อื่น ๆ / response ไม่ใช่ JSON | `BAD_RESPONSE` | ✘ |

### คำถามถึงฝ่ายทะเบียนเรื่องข้อมูล

1. **นักศึกษาคนเดียวหลายวุฒิ** (เช่น ป.ตรี แล้วต่อ ป.โท) ใช้ `studentCode` คนละรหัสใช่หรือไม่ — ระบบรองรับหลายระเบียนต่อเลขบัตรเดียว (จะเข้าคิวให้เจ้าหน้าที่เลือก)
2. **ข้อมูลก่อนยุคดิจิทัล** ที่ไม่มีวันสภาอนุมัติ ควรส่ง `councilApprovalDate: null` + `requiresManualReview: true` ได้หรือไม่
3. **การเพิกถอนวุฒิ** บันทึกเป็นสถานภาพในระบบทะเบียนหรือไม่ และ `updatedAt` เปลี่ยนตามหรือไม่
4. **ชื่อภาษาอังกฤษ** มีครบทุกระเบียนหรือเฉพาะบางปีการศึกษา
5. เลขบัตร/พาสปอร์ตที่ **เปลี่ยนภายหลัง** (เช่น ต่างชาติได้สัญชาติไทย) เก็บอย่างไร

## 6. ข้อมูลตัวอย่างที่ขอ (ปกปิดข้อมูลส่วนบุคคลแล้ว)

เพื่อตรวจ mapping ก่อนเชื่อมต่อจริง (spec ข้อ 10 รายการที่ 2) — ใช้ชื่อสมมติและเลขบัตรสมมติที่ผ่าน checksum ได้ แต่ขอให้ **โครงสร้างและลักษณะข้อมูลตรงกับของจริง** ครอบคลุม:

- สำเร็จการศึกษาปกติ ทุกระดับ (ตรี / โท / เอก)
- เกียรตินิยมอันดับ 1 และ 2
- กำลังศึกษา, พ้นสภาพ/ลาออก, ถูกเพิกถอนวุฒิ
- ชื่อ-นามสกุลซ้ำกันคนละคน
- คนเดียวมีหลายวุฒิ
- นักศึกษาต่างชาติที่มีเฉพาะพาสปอร์ต
- ข้อมูลเก่าที่ฟิลด์ไม่ครบ (ไม่มีวันสภาอนุมัติ / ไม่มีชื่ออังกฤษ / ไม่มี GPA)
- สภายังไม่อนุมัติปริญญา

## 7. การจัดการข้อมูลฝั่ง Krirk Verify (สำหรับประกอบการพิจารณาของฝ่ายทะเบียน)

- เลขบัตร/พาสปอร์ต **ไม่เก็บเป็นข้อความธรรมดา** — เก็บเป็น HMAC-SHA256 (ใช้ค้นหา) และ AES-256-GCM (ใช้แสดงเมื่อเจ้าหน้าที่กดดูเลขเต็ม ซึ่งถูกบันทึกใน Audit Log)
- การแสดงผลต่อผู้ขอภายนอกใช้เลขแบบปิดบังเสมอ
- ผลที่อนุมัติแล้วเก็บเป็น snapshot — ถ้าข้อมูลทะเบียนเปลี่ยนภายหลัง ผลเดิมไม่เปลี่ยน
- ทุกการเข้าถึงข้อมูลบันทึกใน Audit Log พร้อมผู้ใช้ เวลา และ IP
- API key เก็บเป็นตัวแปรสภาพแวดล้อมบนเซิร์ฟเวอร์ ไม่อยู่ในซอร์สโค้ด

## 8. การทดสอบร่วม

1. ฝ่ายทะเบียนเปิด endpoint บนสภาพแวดล้อม UAT พร้อมข้อมูลตัวอย่างตามข้อ 6
2. ทีมพัฒนาตั้ง `REGISTRY_CLIENT=http` บนเครื่อง UAT → หน้า **ซิงก์ข้อมูล** ต้องแสดงสถานะเชื่อมต่อปกติ
3. รัน sync เต็มชุด → จำนวน "ดึงมา" ตรงกับ `total` · จำนวน "ไม่ถูกต้อง" เป็น 0
4. ทดสอบตรวจสอบวุฒิทุกกรณีในข้อ 6 → ผลอนุมัติอัตโนมัติ/เข้าคิวตามกฎ (spec ข้อ 4.2)
5. ทดสอบ API key ผิด, ปิด API ชั่วคราว → ระบบแสดงข้อผิดพลาดที่ถูกต้อง และยังค้นหาจากข้อมูลที่ sync ไว้ได้
6. ตกลงวันเปิดใช้ production และเปลี่ยน key เป็นชุด production

## ภาคผนวก — Mock API อ้างอิง

ระบบมี Mock API รูปแบบเดียวกับเอกสารนี้ ใช้ดูตัวอย่าง response จริงได้บนเครื่องพัฒนา (`MOCK_REGISTRY_ENABLED=true`):

```bash
curl "http://localhost:3000/api/mock/registry/health"
curl "http://localhost:3000/api/mock/registry/students?page=1&pageSize=5"
curl "http://localhost:3000/api/mock/registry/students/6112345679"
```

รูปแบบข้อมูลกำหนดไว้ในโค้ดที่ `src/lib/integrations/registry/types.ts` (Zod schema) และ client ที่ `http-client.ts`
